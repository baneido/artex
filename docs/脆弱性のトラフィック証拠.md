# 脆弱性の複数トラフィック証拠

脆弱性詳細の「関連トラフィック」では、ページをまたいだ複数選択、用途と説明、並び替え、関連付けの解除ができます。トラフィックページでも記録を複数選び、既存の脆弱性 1 件へまとめて関連付けられます。タスク継承の脆弱性証拠は読み取り専用で、変更するには元タスクへ入る必要があります。

システム設定の「Agent によるトラフィックの自動関連付け」は既定でオフです。読み書きの API は `/api/settings` の `agent_traffic_binding` です。オンにすると、リクエストとレスポンスの参照、ツール呼び出し、プロンプトによる Token 消費が増えます。次の Agent ターンから新しい設定を使います。オフのときは自動関連付けのパラメータと追加関連付けツールを隠し、自動関連付けの案内を注入せず、すでに動いているセッションが新たに送った自動関連付けを拒否します。人手の関連付け、トラフィックのキャプチャ、保存済み証拠の読み取りとエクスポートは影響を受けません。

オンのときの既定の流れは「検出事項の登録、レポート Agent の自動起動、トラフィックの照合と関連付け、最新の証拠バージョンに基づくレポート作成」です。報告者は `evidence` に検証コマンド、主要な出力、すでにある実トラフィック ID と用途を残します。レポート Agent は脆弱性の詳細と実行記録を合わせ、`traffic_search` と `traffic_get` で確認してから `bind_finding_traffic` を呼び、最新の `version` を読んでレポートを保存します。スイッチがオフのとき、レポート Agent は生トラフィックの検索と読み取りを追加では持たず、自動関連付けもしません。人手で関連付けたスナップショットは読め、レポートは作れます。

既存の呼び出し元との互換を残します。`report_finding` の `traffic_refs` と `evidence_hint_id` は、これまでどおり明示的にその場で関連付けできます。関連付けは任意です。TCP など HTTP 以外の脆弱性、未収集、正確な記録が見つからない場合は、参照を省いても報告とレポート作成はできます。コマンド出力やログなど、ほかの検証できる証拠は残します。関連付けなかった理由を書くことを勧めますが、必須項目は増やしません。送った ID はすべて有効で、本文が完全でなければなりません。1 件でも失敗すると、その回の関連付け操作はロールバックします。報告と同時の明示的な関連付けが失敗したときは、報告全体がロールバックします。同じスナップショットを重ねて追加しても関連付けは増えず、説明も上書きしません。

## Agent の番号とレポートのバージョン

`report_finding` に任意パラメータを追加しました。配列の順が最初の証拠順です。

```json
{
  "traffic_refs": [
    {"traffic_id": "実際のトラフィックID", "role": "baseline", "note": "正常なアカウントのリクエスト"},
    {"traffic_id": "別の実際のトラフィックID", "role": "proof", "note": "再現リクエスト"}
  ]
}
```

用途は `baseline`（正常時の対照）、`proof`（脆弱性の証明）、`verification`（追加の検証）、`supporting`（補助証拠。既定）です。先に `traffic_search` と `traffic_get` で実記録を照合します。ドメインと時刻は候補の絞り込みにだけ使い、タスクの帰属は推定しません。

プロンプトは [CyberStrikeAI の脆弱性報告ツール案内](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go) を参考にし、このプロジェクトの任意関連付けの約束に合わせています。パケットが無い理由の必須チェックは入れません。ID を推測してはならず、パケットを埋めるためだけに再探索もしません。

戻り値の 1 行目はこれまでどおり `finding recorded: <探索ノード ID>` です。続く JSON が、独立した脆弱性レコード `finding_id`、探索ノード `finding_node_id`、関連付けの要約を渡します。

- `get_finding_traffic(finding_id)` は**独立した脆弱性レコード ID** を使います。順序付きの一覧と `version` を返します。`binding_id`、`side=request|response`、`offset`、`length` を渡すと分割して読め、1 区間は最大 8192 バイトです。
- `update_finding_report` の `finding_id` は**これまでどおり探索ノード ID** です。追加した `evidence_version` には、実際に読んだバージョンを入れます。生成中に証拠が変わると、古いバージョンの書き込みは拒否されます。読み直してから生成し直す必要があります。
- 古いレポート呼び出しがバージョンを渡さないとき、既存のトラフィック証拠を上書きしたとは言いません。関連付け、説明、用途、並び順が変わったあと、既存レポートは更新待ちと示します。

自動関連付けをオンにすると、`add_hint` と `add_task_hint` は、1 件のヒント、または一括 `hints` の各要素に `traffic_refs` を保存できます。Planner が代わりに報告するときは `evidence_hint_id` を渡し、このタスクの対応するヒントにある参照を明示して選びます。継承したヒントは参照できません。システムはドメイン、時刻、閲覧記録から関連付けを推測しません。送信に失敗しても、途中の脆弱性は作らず、レポートも先に起動しません。

既存の脆弱性に関連付け漏れがあるときは、`bind_finding_traffic(finding_id, traffic_refs)` で追加できます。再登録は不要です。`list_findings`、`list_task_findings`、`node_detail`、`get_task_node_detail` は、明確な `finding_id` と `finding_node_id` を返します。古い `id` は探索ノードの意味のままです。

起動時は、古いツール schema に任意プロパティを足すだけです。元の既定トラフィックツールの関連付けはレポート Agent まで広げ、追加関連付けツールは既定でレポート Agent に渡します。カスタムの関連付け一覧、プロンプト、説明、有効状態は残します。案内は最終的なツール組み立てのあとでまとめて入れます。報告役はすでにある証拠の引き継ぎを担当し、レポート Agent は照合、関連付け、レポート作成を担当します。プラットフォームの対話にタスク文脈が無いときは、構造化ヒントでタスク Agent へ引き継ぎ、直接は報告しません。タスク完了と判定する前に、すでにある証拠を先に引き継ぎます。パケットが無くても、待つことは強制しません。失敗した `report_finding` はレポート Agent を起動しません。

## API

基本パスは `/api/exploration/findings/{finding_id}/traffic` で、独立した脆弱性 ID を使います。認証は既存のものを使います。`context_task` がタスクの可視性と、継承の読み取り専用を検査します。

| メソッド / 相対パス | リクエストと戻り値 |
| --- | --- |
| `GET` | 順序付き要約、証拠バージョン、レポートが採用したバージョン |
| `POST` | `{"traffic_refs":[...]}` を一括で追加 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"説明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`。完全な一覧であること |
| `GET /{binding_id}` | スナップショットのメタデータと、上限付きの本文プレビュー |
| `GET /{binding_id}/body` | `side`、`offset`、`length`。`download=1` で元バイトをすべてダウンロード |

バージョンや並び順の集合が衝突したとき、およびアーカイブ中の書き込みは `409` です。継承への書き込みは `403` です。存在しない、またはその脆弱性に属さない関連付けは `404` です。トラフィックと添付の読み取り、および検証の失敗は、エラーを明示して返します。

## 保存と移行

起動時に PostgreSQL を冪等に移行します。追加するのは `traffic_evidence_snapshots`、`finding_traffic_bindings`、および `findings.evidence_version` と `report_evidence_version`（既定 0）です。過去の文章から関連付けを推測して補うことはしません。

スナップショットには、元のトラフィック ID、収集時刻、URL、メソッド、ステータス、リクエストとレスポンスのヘッダ、本文の長さ、SHA-256 を保存します。本文はハッシュで `<data>/evidence/blobs/<先頭2文字>/<hash>.bin` に置き、削除できる `data/traffic` とは分けます。複数の脆弱性がスナップショットと本文を共有できます。スナップショットに内容更新の API はなく、検証が一致しないと読み取りとエクスポートは失敗します。

元トラフィックの書き込みロックの下で、大きな本文 blob と古いディレクトリ記録を含む完全な本文を読みます。先にファイルを永続化して検証し、そのあと 1 つの PostgreSQL トランザクションで探索ノード、インテント関係、脆弱性、スナップショット、関連付けを書きます。コミットしてから計画者へ通知します。失敗すると参照の無いファイルが残ることがありますが、途中までの業務レコードは作りません。

PostgreSQL の advisory lock `7337741004` が、証拠ファイルと SQL 参照を調整します。タスク行ロックは、アーカイブ待ちのあとの証拠変更を禁じます。復元は、本文のインストールからメタデータのコミットまで証拠ロックを保持します。脆弱性の削除は関連付けをカスケードで外します。

クリーナーは 1 時間ごとに動き、参照が無く、進行中の操作でもない内容だけを回収します。少なくとも 24 時間は遅らせます。通常のトラフィック掃除は証拠ディレクトリに触れません。ホットデータをバックアップするときは、PostgreSQL と `data/evidence` を一緒にバックアップします。

## エクスポートとアーカイブ

Markdown には順序付きの証拠一覧とバージョンを含めます。JSON にはメタデータを含めます。CSV には件数と binding ID を足します。`md-zip` は脆弱性の Markdown を残し、次を付けます。

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown は相対リンクでメッセージを参照します。ダウンロードを送る前に、添付のコピー、ハッシュ検証、圧縮、ディスク同期、および ZIP 全エントリの CRC 読み取り検証を終えます。欠落や破損があると、ダウンロード全体が失敗します。完全な添付はバイナリの元バイトを残します。

アーカイブ v3 は脆弱性の関連付けに沿ってスナップショットと本文を集め、元のトラフィックやドメインには依存しません。パッケージの検証が終わってからホットデータを掃除します。共有証拠は残します。復元は、インストールする本文を先に検証し、そのあとトランザクションでメタデータと関連付けを戻します。失敗したら再試行できます。v1 と v2 も復元でき、欠けている新しいフィールドは明示的に 0 で補います。

## 検証と境界

テストパッケージごとに、独立して新規作成した PostgreSQL のテスト用データベースを `ARTEX_PG_DSN` で指定します。残ったタスクやモデルのフィクスチャがバックグラウンド実行を起こさないようにします。関係するパッケージのテストをすべて走らせ、設定不足によるスキップが無いことを確認します。

```sh
# 各パッケージの実行前に、ARTEX_PG_DSN をそのパッケージ用の独立したテスト用データベースへ設定する。明示した設定の失敗はエラーにしなければならない。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証には `npx tsc --noEmit`、影響を受けたファイルの Biome チェック、Webpack ビルド、`NEXT_EXPORT=1` の静的エクスポートを含めます。実行中の開発サーバーを上書きしないよう、独立したキャッシュディレクトリを使います。

このマシンでのエンドツーエンド受け入れは、独立したポート、制御した HTTP とドメイン HTTPS の目標、一時データディレクトリを使い、2 つの関連付け入口、ページをまたいだ選択、並び順と説明、エラー表示、継承の読み取り専用、ダウンロード、および元トラフィック削除後のエクスポート、アーカイブ、ホット本文の回収、復元とハッシュ検証を覆います。

初版はグローバルな証拠調整ロックを使います。大量の関連付けやエクスポート、遅い添付ダウンロードのあいだ、ほかの証拠操作は待つことがあります。記録が無い、または完全な本文が無いときは、証拠を作り上げることはできません。この機能はキャプチャのスイッチを変えず、HTTPS で IP に直接アクセスするときの証明書の問題も扱いません。
