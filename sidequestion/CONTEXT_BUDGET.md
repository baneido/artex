# サイドの長い対話とコンテキスト予算

2026-09-11 の修正です。以前の実装はリクエスト JSON の文字数をそのまま token とみなし、主タスクの 32K 出力予約を継承していました。そのため HTML、JS、ツール結果が多いと、正常なサイド質問を早く拒否していました。

## オープンソース実装の照合

- [Grok CLI のサイドコンテキスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739): 直近のユーザーとアシスタントのテキストから断片を取ります。文字予算は約 2000 で、1 件あたり最大 400 文字です。この経路では連続したサイド質問の履歴を保持しません。
- [Grok CLI の独立リクエスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts): 独立したキャンセルシグナルです。モデルが対応するとき出力上限は 2048 tokens です。ツールは渡しません。
- [Grok CLI の主セッション圧縮](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts): token を見積もり、直近の内容を残し、新しい内容を古い要約へ更新し、ターンをまたぐ切断を扱います。
- [OpenCode のセッション圧縮](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts): リクエスト全体の見積もり、出力とバッファの予約、直近の内容とローリング要約、ツール無しの要約リクエストです。この実装の既定は、直近予算 8000、要約の出力上限 4096 tokens です。
- [OpenCode のオーバーフロー回復](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts): アシスタント出力がまだ始まっていないときだけオーバーフロー回復を試し、回復後の呼び出しは同じ回復経路に入りません。

ARTEX は、独立した出力予算、直近の内容とローリング要約、限られた回復を取り入れています。norma v0.3.6 の構造化メッセージとツールのペアは保ち、Grok のテキスト抜粋はそのまま使いません。OpenCode の主セッション圧縮イベントは、ARTEX の主 transcript には書きません。

## リクエスト予算と実行

- メッセージは norma の、内容ブロックごとの UTF-8 バイト見積もりと 4/3 の余裕を使います。システムプロンプト、ツール schema、メッセージの包みのオーバーヘッドも数えます。見積もりは、モデルの正確な token 数ではありません。
- サイド出力は既定で最大 8192 tokens で、主設定にすでに置いた出力上限も超えません。サービス環境変数 `ARTEX_BTW_MAX_OUTPUT_TOKENS` で 256 から 32768 の上限を設定できます。製品の既定モデルや主タスクのパラメータは変えません。
- 入力予算は、コンテキストウィンドウから出力上限と安全余裕を引いたものです。ウィンドウが未知のときは、プラットフォーム既定の 200K を使います。安全余裕はウィンドウの 5% で、最小 128、最大 8192 tokens です。
- 成功した問答は、増える番号順に 1 バッチ最大 20 組を読みます。原文は最大 20 組を残し、その token 予算は入力予算の 1/4 まで、かつ 16K を超えません。
- 超過した問答はローリング要約へ更新します。要約には履歴の出典とコンテキスト時刻を付けます。過去のアシスタント回答は新しいツール証拠と同じではありません。衝突したときは、最新の主スナップショットを優先します。
- 主コンテキストがまだ長いときは、複製の中の古いメッセージだけを要約し、直近は最大 8K tokens を残します。切断点はツール呼び出しと結果を分けません。大きすぎる 1 組は、まとめて要約に入ります。
- 要約の入力は、実際に残ったウィンドウに合わせて UTF-8 で安全に分割し、出力上限は 2048 tokens です。空の要約、切断、ツール呼び出し、要約予算の超過はキャッシュへ書きません。サイド質問 1 回の要約呼び出しは最大 12 回で、同じ 120 秒のタイムアウトに従います。上限に達すると明示的に失敗し、無限ループしません。
- モデルが最初にコンテキスト超過を返し、まだテキストもツール呼び出しも出していないときは、さらに縮めて最大 1 回再試行します。見積もりサイズが下がらなければ、回復をすぐ止めます。ほかのモデルエラーと、部分的なストリーム出力は、この回復を起動しません。
- 取得できた用量は、要約、失敗した試行、キャンセル時の用量を含め、同じサイド質問リクエストへ足します。Provider が用量を返さないときは 0 としか記録できず、見積もりを実際の用量に見せかけません。

## 永続化と画面

`side_question_sessions.memory` は、古い問答の要約、覆った ordinal、スナップショット識別でキャッシュした主コンテキスト要約を保存します。`side_question_requests.context_info` は、準備段階、実際に再生した組数、要約の使用、予算の見積もりを保存します。

要約を保存するのは、元リクエストがまだ動いていて、クリアバージョンが一致するときだけです。クリアはキャッシュも消します。遅れて来た書き込みが、すでに消したデータを戻すことはありません。新しいスナップショットは、古いスナップショットの要約を再利用しません。要約フィールドは v3 のタスクアーカイブに入ります。古い v3 にフィールドが無いときは空オブジェクトで補い、v1 と v2 は互換のままです。

POST は先に受け付けてリクエストを返します。準備と圧縮はバックグラウンドで行い、入場ロックもデータベーストランザクションも持ちません。SSE と履歴は、準備、問答の整理、複製の圧縮、回答の段階を表示します。圧縮の失敗は、そのサイド質問リクエストの失敗終態として保存します。フロントエンドはエラーを残し、今回失敗した質問の下書きを戻します。フローティング通知で入力欄を隠しません。履歴のポーリングは、送信エラーを消しません。
